# **1\. 핵심 철학**

**"기록은 흐름(Timeline)을 따르고, 요약은 논리(Why)를 따릅니다." 본 가이드는 시간순의 작업 일지로 작업의 맥락을 보존하고, 기술 문서로 모듈 단위의 큰 그림과 기술적 의사결정 근거를 공유하여 팀의 개발 연속성을 보장합니다.**

본 문서는 문서 작업을 작업 일지와, 기술 문서로 나누어 구분합니다. 작업 일지는 작업 과정의 흐름을 기록하고, 기술 문서는 작업일지의 흐름을 요약해 시도 \- 문제 발생 \- 해결의 흐름으로 작성합니다. **기록은 흐름을 따라, 요약은 해결의 이유(Why)를 중심**으로 작성합니다.

### **\[핵심 원칙 요약\] 4가지 핵심 원칙**

* **기록의 이원화 : 과정은 작업 일지(시간순), 결과는 기술 문서(논리)**  
* **논리적 구조 :** 이슈 발생 시 **\[시도 \- 문제 \- 해결\]** 구조를 따르며, 단순 구현은 이 과정을 생략  
* **의사결정 근거** : 해결책 작성 시 ‘**왜 이 기술인가**’에 대한 타당성을 증명해야 한다.  
* **시각화 원칙** : **Mermaid문법** 기반의 도표를 활용해 전달력을 높인다.

## **2\. 작업 일지와 기술 문서**

문서 작업은 작업 일지 작성과 기술 문서 작성으로 나뉜다.

### **\[작업 일지\] 작업 일지 작성**

**1\. 일일 작업 일지**

* **Naming Example :** \[일일 작업 일지\]2026-02-08  
* **형태** **:** 마크다운 (이하 MD)  
* **역할 :** 일일 작업 내용을 담는다 내용은 아래를 포함한다.  
  * **작업 개요:** 하루 동안 작업한 내용의 개요  
  * **문제 사항, 변경 사항, 주요 성과:** 문제 사항에 대해 주요 성과와 변경 사항을 Before, After구조로 나타낸다. 주요 성과 부분에는 발생한 문제 사항을 **왜(Why)** 이런 식으로 풀어냈는 지에 대한 설명이 포함되어야 한다. (예 : 가장 성능 부하가 적은 방법, 프로젝트에 알맞는 기술)  
  * **상세 시스템 사용 가이드:** 주요 성과와 변경 사항 부분에서 바뀐 부분에 대한 사용자 사용 가이드를 작성한다. 스크립트를 새롭게 바꾸었다면 그 스크립트에 대한 사용 가이드를 포함 해야 한다.  
  * **문제 사항의 재현 방법** : 해결한 문제에 대해 문제 상황 재현 방법을 기록한다.  
* **규칙 :**  
  * **흐름 유지**  : 기록은 흐름을 따른다는 원칙을 따라 **한 번 작성한 작업 일지는 수정 하지** 않는다. \[A\]에 대한 작업이 A, A\`, A\`\` 3회에 걸쳐 작업 했다면 3번 모두 기록에 남기고, 최종 작업물 A\`\`에 대한 가이드가 남아야한다.

**2.주간 작업 일지**

* **Naming Example :** \[주간 작업 일지\]2026-02-08  
* **형태** **:** 마크다운 (이하 MD)  
* **역할 :** 주간 작성한 일일 작업 일지를 확인해 요약한다.  
  * **작업 개요:** 하루 동안 작업한 내용의 개요  
  * **문제 사항, 변경 사항, 주요 성과:** 문제 사항에 대해 주요 성과와 변경 사항을   
    \[Before, After, 일일 작업 일지 링크\] 구조로 나타낸다.   
* **규칙 :**  
  * **도표 작성 :** 주간 작업물들에 대한 도표를 작성한다 도표 작성은 **Mermaid문법**을 기준으로 한다.

### **\[기술 문서\] 기술 문서 작성**

기술 문서는 동료의 중단 없는 개발을 위한 나침반이며, '시도-문제-해결'의 논리와 기술 검증을 통해 그 자체로 완전한 작업의 연속성을 보장해야 합니다.

**1\. 특정 시스템에 대한 기술 문서 작성**

* **Naming Example:** \[기술 문서\]\[Feature\]  
* **역할:** **주간 작업 일지**와 **일일 작업 일지**를 확인하고 필요한 경우 기능에 대한 스크립트 또한 확인하여 기술 문서를 작성한다.  
  * **문제 해결 타당성** **:**  해결책 제시 시, 여러 대안 중 해당 기술을 채택한 객관적 이유와 타당성을 반드시 명시해야 합니다.  
    단, 특이 사항이나 기술적 난관이 없었던 단순 구현 작업은 '문제 해결' 과정을 생략할 수 있습니다.  
  * **시각화 원칙** : **Mermaid 문법** 기반의 도표를 활용하여 전달력을 높인다.

**2\. 전체 시스템에 대한 기술 문서 작성**

* **Naming Example:** \[프로젝트 통합 기술 문서\]  
* **역할:** **주간 작업 일지**와 **일일 작업 일지 특정 기술 문서**를 확인하고 필요한 경우 기능에 대한 스크립트 또한 확인하여 기술 문서를 작성한다.  
  * **프로젝트 큰 그림** **:** 모듈·피처 단위의 큰 그림과 데이터 흐름을 중심으로 작성한다.  
  * **시각화 원칙** : **Mermaid 문법** 기반의 도표를 활용하여 전달력을 높인다.
